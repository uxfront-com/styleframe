## Overview

The Styleframe CLI is a command-line interface that helps you initialize new projects and build production-ready CSS from your Styleframe configuration. It provides a streamlined workflow from project setup to optimized style generation.

## Why use the CLI?

The CLI helps you:

- **Quick project setup**: Initialize Styleframe configuration and dependencies with a single command.
- **Optimized builds**: Generate production-ready CSS from your configuration files.
- **Flexible output**: Control where and how your styles are generated.
- **Consistent workflow**: Integrate Styleframe into your development and deployment pipelines.

## Installation

Install the CLI as a development dependency:

:::code-group

```bash [pnpm]
pnpm install -g styleframe
```

```bash [yarn]
yarn add -g styleframe
```

```bash [npm]
npm install -g styleframe
```

```bash [bun]
bun add -g styleframe
```

:::


## Commands

The CLI provides five primary commands: `init` for project setup, `build` for generating CSS output, `check` for finding problems without building, `inspect` for listing what your configuration registers, and `dtcg` for exporting and importing design tokens in DTCG format.

---

### [init]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe init [options]
```

Initialize a new Styleframe project in your current directory.
::
::

#### Options

| Option | Alias | Type | Default | Description |
|--------|-------|------|---------|-------------|
| `--cwd` | `-d`, `--dir` | `string` | `process.cwd()` | Directory where the project will be initialized |


#### Usage

::tabs
:::tabs-item{icon="i-lucide-terminal" label="Current Directory"}

```bash
styleframe init
```

:::
:::tabs-item{icon="i-lucide-terminal" label="Specific Directory"}

```bash
styleframe init --cwd ./my-project
styleframe init -d ./my-project
```

:::
::

1. Creates a `styleframe.config.ts` file with basic configuration
2. Creates or updates `tsconfig.json` with styleframe includes
3. Adds all `styleframe` packages to your `package.json` dependencies
4. Detects and configures your framework (Vite or Nuxt), if applicable
5. Skips creating files that already exist (won't overwrite existing config)

::tip{icon="i-lucide-lightbulb"}
**Pro tip**: After running `init`, don't forget to run `npm install` to install the added dependencies.
::

### [build]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe build [entry] [options]
```

Build your Styleframe project and generate CSS output files.
::
::

#### Options

| Option | Alias | Type | Default | Description |
|--------|-------|------|---------|-------------|
| `entry` | - | `string` | `styleframe.config.ts` | Entry point file(s) for the build |
| `--outputDir` | `-o`, `--out` | `string` | `styleframe` | Output directory for built files |
| `--clean` | - | `boolean` | `false` | Clean output directory before build |


#### Usage

::tabs
:::tabs-item{icon="i-lucide-terminal" label="Default Build"}

```bash
styleframe build
```

:::

:::tabs-item{icon="i-lucide-terminal" label="Custom Entry"}

```bash
styleframe build my-styles.config.ts
```

:::

:::tabs-item{icon="i-lucide-terminal" label="Custom Output"}

```bash
styleframe build --outputDir dist/styles
styleframe build -o dist/styles
styleframe build --out dist/styles
```

:::
::

1. Loads your Styleframe configuration from the entry file
2. Processes all styles, variables, themes, and utilities
3. Generates optimized CSS files in the specified output directory


The build command generates a structured output directory:

```
styleframe/
├── index.css          # Main compiled CSS
└── index.ts           # Main compiled TypeScript
```

#### Warnings and exit codes

Before it writes anything, the build checks your configuration with [`validate()`](/docs/api/instance#strict) and prints one warning line for each problem it finds: the code, where you made the mistake and what's wrong, with the closest token name when there is one.

```
WARN  unresolved-reference recipe "button" › base › background: Reference "@color.brnad" resolves to no variable. Did you mean "@color.brand"?
```

The exit code tells a script or an agent whether the build worked, so you can trust it in CI:

| Exit code | When |
|-----------|------|
| `0` | The build wrote its files. Warnings don't change this, unless `strict` is on. |
| `1` | The build failed, like when the output directory can't be written, or your instance sets [`strict: true`](/docs/api/instance#strict) and the check found a problem. Under `strict`, nothing is written. |

### [check]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe check [entry] [options]
```

Check your Styleframe configuration for problems without building it or writing any files.
::
::

#### Options

| Option | Alias | Type | Default | Description |
|--------|-------|------|---------|-------------|
| `entry` | - | `string` | `styleframe.config.ts` | Entry point file to check |
| `--json` | - | `boolean` | `false` | Print the result as one JSON document on stdout |
| `--typecheck` | - | `boolean` | `false` | Also type-check the entry file with your project's TypeScript |

#### Usage

::tabs
:::tabs-item{icon="i-lucide-terminal" label="Default Check"}

```bash
styleframe check
```

:::

:::tabs-item{icon="i-lucide-terminal" label="JSON Output"}

```bash
styleframe check --json
```

:::

:::tabs-item{icon="i-lucide-terminal" label="Type Check"}

```bash
styleframe check --typecheck --json
```

:::
::

1. Loads your Styleframe configuration from the entry file
2. Runs [`validate()`](/docs/api/instance#strict) on it and prints one warning line per problem
3. Exits with `0` when it finds no problem and `1` when it finds any, whether or not `strict` is on

When the entry file doesn't exist, `check` prints `Config file not found` on stderr and exits with `1`, so a mistyped path never passes as a clean config.

With `--json`, the command prints one document on stdout and nothing else, so an agent or a script can parse it directly. When the config file is missing or fails to load, it prints the error on stderr instead, nothing on stdout, and exits with `1`.

```json
{
  "ok": false,
  "diagnostics": [
    {
      "code": "unresolved-reference",
      "severity": "warning",
      "message": "Reference \"@color.brnad\" resolves to no variable. Did you mean \"@color.brand\"?",
      "path": "recipe \"button\" › base › background",
      "suggestion": "color.brand"
    }
  ]
}
```

Each diagnostic has a stable `code` (`unresolved-reference`, `undefined-theme-override` or `duplicate-variable`), a `severity` that's `error` under `strict` and `warning` otherwise, a `message`, the `path` to where the problem was made and a `suggestion` when a registered token name is within two edits.

#### Type checking

The `--typecheck` flag also runs TypeScript on your entry file, so a typo like a default variant that isn't one of the recipe's options shows up in the same call as the problems `validate()` finds. It uses the `tsc` that your project installs and the compiler options of the `tsconfig.json` nearest to the entry file, or `strict` defaults when there's none. Only the entry file and the files it imports are checked, not the rest of your project.

To run `tsc` on that one file, the command writes a temporary tsconfig into your project's `node_modules/.cache` and removes it when it's done. That way your `types` and `@types` packages resolve as they do for your project. When `node_modules` is read-only, like under Nix, it uses your system's temporary directory instead. It turns off `incremental` for the run, and `composite` too, with `declaration` left on, so your `.tsbuildinfo` and output directory stay as they are.

Each type error becomes a diagnostic with the code `typescript`, the severity `error`, its `TS` number at the start of the message and the file and line as its `path`:

```json
{
  "code": "typescript",
  "severity": "error",
  "message": "TS2322: Type '\"medium\"' is not assignable to type '\"md\" | \"sm\" | undefined'.",
  "path": "styleframe.config.ts:4"
}
```

The CLI doesn't bundle TypeScript, since it's an optional peer dependency. When your project doesn't install `typescript`, `check --typecheck` prints `TypeScript not found` on stderr and exits with `1`.

::tip{icon="i-lucide-lightbulb"}
**Pro tip**: Run `styleframe check --json` after every change an agent makes to your configuration. It writes no files and reports every problem in one pass.
::

### [inspect]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe inspect [entry] [section] [options]
```

List the variables, themes, utilities, modifiers and recipes your configuration registers, without building it or reading its CSS.
::
::

#### Options

| Option | Alias | Type | Default | Description |
|--------|-------|------|---------|-------------|
| `entry` | - | `string` | `styleframe.config.ts` | Entry point file to inspect |
| `section` | - | `string` | - | One section to print: `variables`, `themes`, `utilities`, `modifiers` or `recipes` |
| `--json` | - | `boolean` | `false` | Print the result as one JSON document on stdout |

#### Usage

::tabs
:::tabs-item{icon="i-lucide-terminal" label="Everything"}

```bash
styleframe inspect
```

:::

:::tabs-item{icon="i-lucide-terminal" label="One Section"}

```bash
styleframe inspect styleframe.config.ts themes
styleframe inspect themes
```

:::

:::tabs-item{icon="i-lucide-terminal" label="JSON Output"}

```bash
styleframe inspect --json
styleframe inspect recipes --json
```

:::
::

The command prints the snapshot that [`inspect()`](/docs/api/instance#inspecting-an-instance) returns, with one list per section:

```
variables (1)
  color.brand  --color--brand: #6366f1

themes (1)
  dark  .dark-theme, [data-theme="dark"]
    color.brand: #818cf8

utilities (1)
  background-color
    values: brand
    modifiers: hover
    classes: _background-color:brand _hover:background-color:brand

modifiers (1)
  hover

recipes (1)
  button
    size: sm, md (default: md)
```

With `--json`, it prints one document on stdout and nothing else: the whole snapshot, or an object with only the section you asked for, like `{ "themes": [...] }`. When you pass a section name on its own, like `styleframe inspect themes`, the command reads it as the section and inspects `styleframe.config.ts`. An unknown section or a missing config file prints an error on stderr and exits with `1`.

::tip{icon="i-lucide-lightbulb"}
**Pro tip**: Run `styleframe inspect --json` before an agent edits your configuration. It shows the token names, the themes a preset adds, the class names a utility emits and each recipe's variant options, so the agent doesn't have to read the source or the generated CSS.
::

### [dtcg]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe dtcg <subcommand> [options]
```

Export Styleframe variables to and import them from spec-conformant DTCG (Design Tokens Community Group) JSON. The export output is consumed by the `@styleframe/figma` plugin (which performs the DTCG → Figma value conversion) and any other DTCG-compatible tooling; the import command generates Styleframe TypeScript code from a DTCG JSON file.
::
::

##### Usage

#### [dtcg import]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe dtcg import [options]
```

Generate Styleframe TypeScript code from DTCG format JSON (e.g. produced by the `@styleframe/figma` plugin's Export action or the Variables REST API).
::
::

##### Options

| Option | Alias | Type | Default | Description |
|--------|-------|------|---------|-------------|
| `--input` | `-i` | `string` | - | Input DTCG JSON file or directory containing `tokens.json` (required) |
| `--output` | `-o` | `string` | `tokens.styleframe.ts` | Output Styleframe TypeScript file path |
| `--composables` | - | `boolean` | `true` | Use @styleframe/theme composables (useColorDesignTokens, useSpacingDesignTokens, etc.) |
| `--rem` | - | `boolean` | `false` | Use rem units for dimensions instead of px |
| `--baseFontSize` | - | `string` | `16` | Base font size for rem conversion (in pixels) |
| `--instanceName` | - | `string` | `s` | Name for the Styleframe instance variable |

##### Usage

::tabs
:::tabs-item{icon="i-lucide-terminal" label="Directory Import"}

```bash
styleframe dtcg import -i tokens/
```

:::
:::tabs-item{icon="i-lucide-terminal" label="Single File"}

```bash
styleframe dtcg import -i tokens.json
```

:::
:::tabs-item{icon="i-lucide-terminal" label="Custom Output"}

```bash
styleframe dtcg import -i tokens/ --output src/tokens.styleframe.ts
styleframe dtcg import -i tokens/ -o src/tokens.styleframe.ts
```

:::
:::tabs-item{icon="i-lucide-terminal" label="With rem Units"}

```bash
styleframe dtcg import -i tokens/ --rem
styleframe dtcg import -i tokens/ --rem --baseFontSize 14
```

:::
:::tabs-item{icon="i-lucide-terminal" label="Without Composables"}

```bash
styleframe dtcg import -i tokens/ --composables false
```

:::
::

1. Reads `tokens.json` from the input path (or a single file); auto-detects a sibling `tokens.resolver.json` for multi-mode support
2. Converts DTCG format to Styleframe variables and themes
3. Generates TypeScript code with proper imports and variable definitions
4. Optionally uses @styleframe/theme composables for common patterns

### [figma]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe figma <subcommand> [options]
```

Export and import Figma-compatible DTCG per-mode files. Unlike the spec-conformant `dtcg` commands, `figma` uses only the three types Figma supports (`number`, `color`, `string`), flattens structured values to primitives, and writes one complete `.tokens.json` file per mode — ready for direct import into Figma via the [Styleframe Figma Plugin](/docs/getting-started/integrations/figma-plugin).
::
::

---

#### [figma export]{.text-primary}

::field-group
::field{type="command"}

```bash
styleframe figma export [options]
```

Export Styleframe variables to Figma-compatible DTCG per-mode files.
::
::

##### Options

| Option | Alias | Type | Default | Description |
|--------|-------|------|---------|-------------|
| `--config` | `-c` | `string` | `styleframe.config.ts` | Path to the Styleframe config file |
| `--output` | `-o` | `string` | `.` | Output directory for per-mode `.tokens.json` files |
| `--collection` | `-n`, `--name` | `string` | `Design Tokens` | Collection name embedded in the export |

##### Usage

::tabs
:::tabs-item{icon="i-lucide-terminal" label="Default Export"}

```bash
styleframe figma export
```

:::
:::tabs-item{icon="i-lucide-terminal" label="Custom Output Dir"}

```bash
styleframe figma export --output tokens/
styleframe figma export -o tokens/
```

:::
:::tabs-item{icon="i-lucide-terminal" label="Custom Collection"}

```bash
styleframe figma export --collection "My Design System"
styleframe figma export -n "My Design System"
```

:::
::

1. Loads your Styleframe config and builds a spec-conformant DTCG document
2. Flattens rich DTCG types to Figma's model (`dimension` → `number`, `cubicBezier` → `string`, etc.)
3. Clamps colour components to the `[0, 1]` range and forces sRGB
4. Writes one complete `{ModeName}.tokens.json` per mode (e.g. `Default.tokens.json`, `Dark.tokens.json`)

::tip{icon="i-lucide-info"}
The Figma export is a one-way simplification layer on top of the rich `dtcg export`. For spec-conformant DTCG output (e.g. for Style Dictionary or Tokens Studio), use `styleframe dtcg export` instead.
::

## Best Practices


- **Use npm scripts**: Define CLI commands in your `package.json` for consistent execution across your team.
- **Version control configs**: Commit your `styleframe.config.ts` to ensure consistent styling across environments.
- **Integrate with CI/CD**: Run `styleframe check` and `styleframe build` in your deployment pipeline. Both exit with `1` when they fail, so the pipeline stops.
- **Organize output**: Use `--outputDir` to organize generated files according to your project structure.
- **Descriptive naming**: Use clear names for multiple configs like `styleframe.theme.config.ts` or `styleframe.components.config.ts`.


::warning{icon="i-lucide-alert-triangle"}
**Use native integrations**: We recommend using native integrations with [Vite](/docs/getting-started/installation/vite) and other tools for building projects using styleframe.
::

## FAQ

::accordion

:::accordion-item{label="Command not found: styleframe" icon="i-lucide-circle-help"}
Ensure `styleframe` is present in your `node_modules/.bin` directory. Alternatively, try running the command with `npx`:

```bash
npx styleframe init
```
:::

:::accordion-item{label="Configuration file not found" icon="i-lucide-circle-help"}
The CLI looks for `styleframe.config.ts` by default. Either create this file or specify your config path:

```bash
styleframe build path/to/your/config.ts
```
:::

:::accordion-item{label="Can I use JavaScript instead of TypeScript for config?" icon="i-lucide-circle-help"}
Currently, the CLI expects TypeScript configuration files (`.ts`). You can still write your application code in JavaScript while using TypeScript only for the config file.
:::

:::accordion-item{label="How do I use multiple configuration files?" icon="i-lucide-circle-help"}
Run the build command with different entry points and output directories:

```bash
styleframe build styleframe.theme.config.ts -o dist/theme
styleframe build styleframe.components.config.ts -o dist/components
```
:::

:::accordion-item{label="Build fails with module errors" icon="i-lucide-circle-help"}
Ensure all dependencies are installed and your configuration file has valid TypeScript syntax. Verify that you've exported your Styleframe instance as the default export.
:::

:::accordion-item{label="Does the CLI support custom configuration options?" icon="i-lucide-circle-help"}
Configuration options are defined in your `styleframe.config.ts` file using the [`styleframe()`](/docs/api/instance#configuration-options) function. The CLI respects all configuration options you set there.
:::

:::accordion-item{label="Can I programmatically use CLI commands?" icon="i-lucide-circle-help"}
While primarily designed for CLI use, you can import and use the underlying `build` and `loadConfiguration` functions directly from `@styleframe/loader` in Node.js scripts.
:::

:::accordion-item{label="How do I sync variables with Figma?" icon="i-lucide-circle-help"}
The `dtcg` command handles both directions:

1. **Code → Figma**: Run `styleframe dtcg export` to generate spec-conformant DTCG JSON files, then import them into Figma using the `@styleframe/figma` plugin
2. **Figma → Code**: Export your Figma variables as DTCG JSON via the plugin, then run `styleframe dtcg import -i tokens/` to generate Styleframe code

```bash
# Export Styleframe → DTCG JSON (importable by the Figma plugin)
styleframe dtcg export -o tokens/

# Import Figma → Styleframe
styleframe dtcg import -i tokens/ -o src/tokens.styleframe.ts
```
:::
